# Решения и допущения

Где ТЗ можно понять по-разному, я выбрал вариант ниже. Пункт 1 согласован с работодателем, остальные — мои решения.

## Права и роли

1. **Удаление настоящее, история хранится отдельно.** Постановщик удаляет задачи и объекты по-настоящему. История лежит в своей таблице без внешнего ключа на задачу, поэтому переживает удаление. Сам факт удаления пишется в историю событием `deleted` со снимком названия задачи и объекта. При удалении объекта удаляются его задачи, и по каждой появляется своя запись `deleted`. В интерфейсе удалённые задачи не видны. Факт удаления можно посмотреть в панели Supabase: Table Editor → `task_history`, фильтр `event = deleted`, или SQL `select * from task_history where event = 'deleted'`. _Согласовано с работодателем._
2. **Принять или вернуть задачу может любой постановщик**, а не только автор. Постановщиков несколько, и по ТЗ они «видят всё».
3. **У пользователя одна роль.** Она хранится в `profiles.role`. Сам пользователь изменить роль не может: на `profiles` у него нет прав на запись. Меняет её админ в панели Supabase. Роль не берётся из `user_metadata`, потому что эти данные пользователь может править сам. Пользователь без профиля не видит ничего.
4. **Исполнитель в карточке объекта видит название, адрес и только свои задачи.** Объекты, где у него нет задач, ему не видны.
5. **Профили видны всем вошедшим:** `id`, имя и роль, чтобы показывать автора, историю и выбирать исполнителя. Email и прочие данные авторизации не открыты.

## Задачи

6. **Исполнитель обязателен** при создании задачи. Им может быть только пользователь с ролью «Исполнитель»; это проверяет база.
7. **Что постановщик может редактировать:**
   - название и описание — пока задача не принята;
   - объект и исполнителя — только в статусе «Новая»;
   - принятую задачу менять нельзя, только удалить;
   - статус — никогда, только переходами.
8. **Комментарий** обязателен при возврате на доработку и не может состоять из одних пробельных символов (пробелы, переносы строк, табуляция): база срезает их по краям через `btrim` и отклоняет пустой результат. В остальных переходах он не нужен (интерфейс его не спрашивает, база принимает).
9. **История** пишет создание («— → Новая»), каждую смену статуса и удаление. Её видят обе роли: исполнитель — по своим задачам, включая записи постановщиков.

## Экраны

10. **«Мои задачи» есть только у исполнителя:** все его задачи, принятые внизу. Постановщик начинает со списка объектов.
11. **Объект с задачами удалить можно**, но после подтверждения, где указано, сколько задач удалится.
12. **Статусы в базе на английском** (`new`, `in_progress`, `review`, `accepted`, `rework`), в интерфейсе — по-русски.

## Технические решения

- **Статус меняется только функцией `transition_task`.** У пользователей нет права UPDATE на колонку `status`. Таблица допустимых переходов `task_status_transitions` одна и лежит в базе. По ней работает функция, и по ней же интерфейс решает, какие кнопки показать.
- **Если клиент сам присылает служебные поля** (`status`, `author_id`, `created_at`, `created_by`), запрос **отклоняется целиком** с ошибкой `42501`, а не перезаписывается молча. Эти колонки клиенту просто не разрешено задавать; значения ставит база по умолчанию. Так атакующий не получает «успешный» ответ.
- **Гонка переходов.** `transition_task` блокирует строку задачи (`select … for update`). Второй одновременный запрос ждёт, видит уже новый статус и получает отказ. Тест гонки проверен мутацией: без `for update` он краснеет, с ним проходит стабильно.
- **Удаление объекта сделано триггером, а не каскадом.** При каскадном удалении строка объекта исчезает раньше, чем удаляются задачи, и в историю не попало бы название объекта. Поэтому перед удалением объекта триггер сам удаляет его задачи. Внешний ключ задачи на объект оставлен без каскада: если триггер уберут, удаление объекта с задачами упадёт с ошибкой, а не потеряет историю молча.
- **Демо-пользователей создаёт скрипт через Auth Admin API, а `seed.sql` содержит только данные.** Вставлять пользователей прямо в `auth.users` хрупко: GoTrue падает при входе, если служебные колонки токенов `NULL`, а не пустая строка, и это зависит от версии GoTrue. К тому же нет гарантии, что такая вставка пройдёт в облаке. Admin API — поддерживаемый путь, одинаковый локально и в облаке. Скрипт создаёт пользователей с фиксированными id, и `seed.sql` на них ссылается. Пароли и секретный ключ скрипт берёт только из локального `.env`.
- **`seed.sql` обёрнут в один блок `do $$ … $$`:** `supabase db query -f` выполняет ровно одну команду. Заодно сид применяется целиком или не применяется вовсе.
- **Регистрация закрыта:** `enable_signup = false` локально; в облаке её нужно выключить в панели (инструкция в README).
- **Во фронтенд попадают только URL и publishable key.** Секретный ключ используют только скрипт сида и тесты, а берут его из локального `.env`.

## Что не сделано

- История по удалённым задачам в интерфейсе (она есть в базе, экрана нет).
- Управление пользователями и ролями из интерфейса: по ТЗ это делает админ в Supabase.
- Пагинация, поиск и фильтры, обновление в реальном времени, сброс пароля — в ТЗ их нет.
